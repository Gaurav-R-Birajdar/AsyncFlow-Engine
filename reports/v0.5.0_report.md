## 1. Executive Summary

Phase 2 of the AsyncFlow Engine upgrade introduces production-grade fault tolerance for LLM inference jobs. Prior to this release, a single job failure resulted in silent discard — no retry, no recovery, no audit trail. This release implements:

| Capability | Implementation | Status |
|---|---|---|
| Exponential Backoff Retry | `RQ Retry(max=3, interval=[2,4,8])` at enqueue | ✅ Implemented |
| Redis Dead-Letter Queue | `asyncflow:dlq` LPUSH on final failure | ✅ Implemented |
| DLQ API Inspection | `GET /workflow/dlq` FastAPI endpoint | ✅ Implemented |
| Worker Lifecycle Telemetry | `[QUEUED]` / `[PROCESSING]` / `[RETRYING]` / `[DLQ-SENT]` log tags | ✅ Implemented |

## 2. Architecture Changes

### 2.1 — Data Flow: Retry + DLQ Pipeline

```
POST /workflow/submit
        │
        ▼
  [QUEUED] — routes.py logs job accepted
  queue.enqueue(
    process_workflow,
    retry=Retry(max=3, interval=[2,4,8]),
    on_failure=route_to_dlq
  )
        │
        ▼
  Redis Queue: asyncflow_default
        │
        ▼ (worker picks up job)
  [PROCESSING] — queue_tasks.py: worker executing
        │
        ├─ Attempt 1 → FAILS
        │     │
        │     ▼ (wait 2s)
        │  [RETRYING] — RQ re-queues with 2s delay
        │
        ├─ Attempt 2 → FAILS
        │     │
        │     ▼ (wait 4s)
        │  [RETRYING] — RQ re-queues with 4s delay
        │
        ├─ Attempt 3 → FAILS
        │     │
        │     ▼ (wait 8s)
        │  [RETRYING] — RQ re-queues with 8s delay
        │
        └─ Attempt 4 (final) → FAILS
              │
              ▼ (on_failure callback invoked)
           [DLQ-SENT] — dlq.route_to_dlq()
              │
              ▼
        LPUSH asyncflow:dlq {
          "job_id":        str,
          "workflow_name": str,
          "enqueued_at":   ISO-8601,
          "failed_at":     ISO-8601,
          "attempt":       4,
          "traceback":     str,
          "payload":       {...}
        }
              │
              ▼
        GET /workflow/dlq → returns all DLQ entries
```

### 2.2 — New File: `app/worker/dlq.py`

The central DLQ routing module. Exposes `route_to_dlq` — a function with the exact signature required by RQ's `on_failure` callback protocol:

```python
def route_to_dlq(
    job: Job,
    connection: Redis,
    type_: type[BaseException],
    value: BaseException,
    traceback,
) -> None:
```

**Design decisions:**
- Uses `LPUSH` (not `RPUSH`) — newest failures appear at the head of the list, which is the natural inspection order for `LRANGE asyncflow:dlq 0 -1`.
- Serialises the full traceback as a string via `traceback.format_exception()` — preserves the complete exception chain including `__cause__` for debugging.
- Handles DLQ push failure with `CRITICAL`-level log rather than swallowing — a DLQ that silently drops entries is worse than no DLQ.
- Uses `default=str` in `json.dumps` — prevents `TypeError` on non-serialisable types in the workflow payload (e.g. `datetime`, `Enum`).

### 3.3 — `app/api/routes.py`

**Submit endpoint changes:**
- Imports `Retry` from `rq.job` and `route_to_dlq` from `app.worker.dlq`.
- Builds `retry_policy = Retry(max=settings.RQ_RETRY_MAX, interval=settings.RQ_RETRY_INTERVALS)` per-submission (policy values come from settings, not hardcoded).
- Passes `retry=retry_policy` and `on_failure=route_to_dlq` to `queue.enqueue()`.
- Adds `[QUEUED]` telemetry log including retry policy parameters.

**New endpoint: `GET /workflow/dlq`**

```
GET /workflow/dlq
Response: 200 OK — list[dict] (DLQ entries, newest first)
          503 SERVICE UNAVAILABLE — if Redis is unreachable
```

Implementation:
```python
raw_entries = redis_conn.lrange(dlq_key, 0, -1)
return [json.loads(entry) for entry in raw_entries]
```

Malformed entries are surfaced as `{"error": "malformed DLQ entry", "raw": "..."}` instead of raising 500 — the inspection endpoint must remain available even if a DLQ entry was corrupted.

## 4. Retry Mechanics Deep Dive

### 4.1 — RQ Retry Configuration

```python
Retry(max=3, interval=[2, 4, 8])
```

This means RQ will perform **4 total execution attempts**:

| Attempt | Wait Before | Trigger |
|---|---|---|
| 1 (original) | 0s | Job first dequeued |
| 2 (retry 1) | 2s | After attempt 1 failure |
| 3 (retry 2) | 4s | After attempt 2 failure |
| 4 (retry 3) | 8s | After attempt 3 failure |
| — | — | `on_failure` → DLQ |

**Why exponential?** GPU inference bottlenecks and Ollama API timeouts are often transient. A 2s gap covers momentary VRAM pressure. A 4s gap covers a brief Ollama restart. An 8s gap covers a longer queue drain. Linear backoff would either retry too aggressively (causing GPU OOM) or wait too long on simple transient errors.

### 4.2 — Retry Scope: Job-Level vs Step-Level

This release implements **two independent retry layers**:

| Layer | Mechanism | Scope | Config |
|---|---|---|---|
| Step-level | `retry_on_failure` flag per step | Single LLM call within `process_workflow` | Per-step in payload |
| Job-level | `RQ Retry(max=3, interval=[2,4,8])` | Entire `process_workflow()` invocation | `RQ_RETRY_MAX` / `RQ_RETRY_INTERVALS` |

The step-level retry (existing, from Phase 2.0) catches `LLMTimeoutError` and `LLMMalformedResponseError` without re-running the entire workflow. The job-level retry (new in v0.5.0) catches crashes that propagate out of `process_workflow()` entirely — schema validation failures, deserialization errors, or unhandled exceptions in the engine layer.

## 5. DLQ Data Model

### 5.1 — Redis Key Structure

```
Type: Redis List
Key:  asyncflow:dlq
Head: Most recently failed job (LPUSH)
Tail: Oldest failed job

LRANGE asyncflow:dlq 0 -1 → all entries, newest-first
LRANGE asyncflow:dlq 0 9  → last 10 failures
LPOP asyncflow:dlq        → dequeue and process one entry
```

### 5.2 — Full Entry Schema

```json
{
  "job_id":        "3a7f2c9e-1b5f-4d8a-b2c1-9f0e7d3a6e8b",
  "workflow_name": "financial-extraction-pipeline",
  "enqueued_at":   "2026-09-02T12:00:00.123456+00:00",
  "failed_at":     "2026-09-02T12:00:42.789012+00:00",
  "attempt":       4,
  "traceback":     "Traceback (most recent call last):\n  File \"...\"\nLLMConnectionError: Cannot connect to Ollama...",
  "payload": {
    "workflow_name": "financial-extraction-pipeline",
    "input_text": "Q3 revenue was $4.2B...",
    "steps": [...]
  }
}
```

## 9. Known Limitations & Future Work

| Item | Notes |
|---|---|
| No DLQ replay endpoint | `GET /workflow/dlq` is read-only. A `POST /workflow/dlq/replay` to re-submit failed payloads is planned for v0.6. |
| DLQ list grows unbounded | No TTL on `asyncflow:dlq`. Production should implement periodic `LTRIM` or a TTL via a Lua script. |
| `attempt` count is approximate | `total_attempts = RQ_RETRY_MAX + 1` is calculated statically; actual attempt count would require RQ job metadata introspection. |
| `_on_job_retried` callback | Defined in `run_worker.py` but not registered in this release (RQ SimpleWorker callback registration API differs by version). Log comes from `dlq.py` instead. |
