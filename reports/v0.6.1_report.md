# AsyncFlow Engine — v0.6.1 Patch Report (Critical Bug Fix)

**Date:** 2026-09-04  
**Author:** Antigravity (AGY)  
**Scope:** Critical bugfix — `process_workflow` silent failure swallowing  
**Version:** `0.6.1` (patch over `0.6.0`)  
**Architect Role:** Elite Distributed Systems Architect — Python / FastAPI / Redis

---

## 1. Executive Summary

v0.6.1 fixes a critical architectural defect that made Phases 2 and 3
(exponential backoff retry and DLQ routing) completely inoperative when
the LLM (Ollama) was unreachable.

The root cause: `process_workflow` caught `LLMConnectionError`, recorded
the step as `FAILED`, then **returned normally** with a result dict.
RQ interprets any normal Python return as a successful job — it stored the
result for 500 seconds (`result_ttl`) and immediately went back to
blocking (`BLMOVE`) for the next job.  The job never saw a retry; it
never entered the DLQ.

The fix is a single architectural principle: **if the workflow cannot
complete, the worker function must raise.  It must never return.**

---

## 2. Bug Anatomy

### 2.1 — Observed Symptom (before fix)

```
worker log:
  [ERROR] Step 'step_summarize' — LLM unreachable (fatal): ...
  [INFO]  [PROCESSING] Workflow 'phase2-full-pipeline-test' finished. Final status: FAILED.

RQ internal log:
  result_ttl=500 seconds          ← RQ stored a "success" result
  BLMOVE asyncflow_default ...    ← Worker went back to idle immediately
```

Expected log (after fix):
```
  [ERROR] [PROCESSING] Workflow '...' aborting — re-raising 'LLMConnectionError' for RQ retry/DLQ.
  <unhandled exception>           ← RQ sees a crash
  [RETRYING] Job '...' attempt 1/4 failed. Re-queueing with backoff 2s.
  ... (wait 2s, 4s, 8s) ...
  [DLQ-SENT] Job '...' permanently failed after 4 attempts. Payload pushed to 'asyncflow:dlq'.
```

### 2.2 — Code Path (before fix)

```python
# queue_tasks.py — process_workflow()

except LLMConnectionError as exc:
    result.status = StepStatus.FAILED
    connection_fatal = True
    break                          # exits while-loop only

# ... falls through to:
if result.status == StepStatus.FAILED:
    # skip remaining steps...
    break                          # exits for-loop

# ... falls through to:
return {"step_results": ..., "final_output": None}
#  ^^^ RQ sees a clean return → marks job SUCCESS → no retry, no DLQ
```

### 2.3 — Why RQ Needs an Unhandled Exception

RQ's job lifecycle state machine:

```
enqueue → [queued] → [started] → function returns? → [finished] (success)
                                → function raises?  → [failed]
                                                         ↓
                                                    retries_left > 0?
                                                    → re-enqueue (backoff)
                                                    → retries_left == 0?
                                                    → on_failure() → DLQ
```

A `return` (with any value, even `None`) always transitions to `[finished]`.
Only an unhandled `raise` transitions to `[failed]` and activates the
retry + DLQ machinery.

## 3. The Fix

### 3.1 — Preserve the causal exception reference

In both failure branches, save the exception before `break`:

```python
# LLMConnectionError branch
except LLMConnectionError as exc:
    ...
    connection_fatal = True
    fatal_exc: BaseException = exc   # ← NEW
    break

# All other exceptions (timeout, malformed, etc.)
except (LLMTimeoutError, LLMMalformedResponseError, Exception) as exc:
    ...
    if attempt >= max_attempts:
        result.status = StepStatus.FAILED
        result.error = f"{exc_label}: {exc}"
        fatal_exc = exc              # ← NEW
```

### 3.2 — Re-raise after recording skip entries

Replace the `break` that exited the for-loop with an explicit `raise`:

```python
if result.status == StepStatus.FAILED:
    # mark remaining steps SKIPPED (unchanged)
    for skipped_step in request.steps[idx:]:
        step_results.append(...)

    # v0.6.1 CRITICAL FIX
    logger.error(
        "[PROCESSING] Workflow '%s' aborting — re-raising '%s' for RQ retry/DLQ.",
        request.workflow_name,
        type(fatal_exc).__name__,
    )
    raise fatal_exc                  # ← RQ sees this; triggers retry/DLQ
```

### 3.3 — Successful path is now unambiguous

The `return` at the bottom of `process_workflow` is now **only reachable
when every step completed successfully**:

```python
    # Chain output: this step's output becomes the next step's input
    current_input = result.output or current_input

# ── All steps completed ──────────────────────────────────────────────
final_output = next(...)
logger.info("[PROCESSING] Workflow '%s' finished successfully — %d step(s) completed.", ...)
return {"step_results": step_results, "final_output": final_output}
```

## 8. Known Limitations (Updated)

| Item | Notes |
|---|---|
| Step results lost on re-raise | When a step fails and we re-raise, the partially collected `step_results` are not persisted anywhere. On retry, the worker starts fresh. A future version could store partial progress in Redis for observability. |
| Replay all-or-nothing | No per-`job_id` single-entry replay (v0.6.0 known limitation, unchanged). |
| DLQ grows unbounded | No TTL or `LTRIM` policy (v0.6.0 known limitation, unchanged). |
