# v1.0.0 Report — Phase 2: MCP Governance Interceptor (SAM-Layer-Inspired Governance)
**Date:** 2026-09-23 | **Version:** v1.0.0 | **Phase:** 2

---

## 1. Summary

Phase 2 introduces an enterprise-grade LLM governance middleware — the **MCP Governance Interceptor** — modelled after a SAM (Sensitive-data Access Management) layer.

The interceptor sits between `_run_llm_step()` output and the step chain propagation inside `process_workflow`. For every `EXTRACT_JSON` and `CUSTOM_PROMPT` step, the raw LLM JSON is:
1. Parsed and validated against an `EnterpriseToolPayload` Pydantic schema.
2. Recursively scanned for PII keys (21 canonical field names, case-insensitive, depth-unlimited).
3. Redacted in-place with `[REDACTED_BY_POLICY]`.
4. Logged to an append-only JSONL audit trail at `data/audit.jsonl`.
5. Replaced in the step output — the next step **never sees raw PII**.

If the interceptor itself fails (unparseable JSON, write error), it raises `GovernanceError(RuntimeError)`, which feeds into the identical exponential backoff + DLQ machinery introduced in Phase 2/3.

## 4. Architecture

```
process_workflow()
    │
    ├── LLMEngine.generate() / generate_json()
    │       └── _run_llm_step()  ──▶  raw_output (str)
    │
    ├── [EXTRACT_JSON or CUSTOM_PROMPT?]
    │       │ YES (and GOVERNANCE_ENABLED=true)
    │       ▼
    │   GovernanceInterceptor.parse_and_sanitize(raw_output, step_id)
    │       ├── json.loads()  ──▶ GovernanceError on JSONDecodeError
    │       ├── EnterpriseToolPayload(**payload)  ──▶ GovernanceError on ValidationError
    │       └── _redact_recursive()  ──▶ (sanitized_dict, redacted_keys)
    │
    ├── [redacted_keys non-empty?]
    │       └── logger.warning("[GOVERNANCE_INTERCEPT] ...")
    │
    ├── AuditLogger.log_event(original, sanitized, step_id, redacted_keys)
    │       └── data/audit.jsonl  ◀── append one JSONL line
    │
    └── output = json.dumps(sanitized_dict)  ──▶  next step / return
```

## 6. Fault Model Integration

| Failure Scenario | Behaviour |
|---|---|
| LLM output is not valid JSON | `GovernanceError` raised → caught by except-all → re-raised → RQ retry → DLQ |
| Pydantic validation error | `GovernanceError` raised → same path |
| `data/audit.jsonl` write fails | `GovernanceError` raised → same path — workflow **blocked** without audit trail |
| Interceptor disabled (`GOVERNANCE_ENABLED=false`) | Step output passes through unmodified; no audit write |
| Non-JSON step types (summarize, translate, etc.) | Interceptor **not invoked** — plain text path unchanged |

Phase 2/3 invariants fully preserved:
- DLQ routing (`route_to_dlq`) unchanged.
- `LLMConnectionError` fatal-raise fix (v0.6.1) unchanged.
- Exponential backoff intervals unchanged.
- External REST API contract unchanged (zero new endpoints).

## 7. Audit Log Schema (`data/audit.jsonl`)

One JSON object per line (UTF-8):

```json
{
  "timestamp": "2026-09-23T12:05:31.842193+00:00",
  "tool_name": "step_extract_employee",
  "redacted_keys": ["ssn", "employee.tax_id"],
  "original_payload": {
    "ssn": "123-45-6789",
    "employee": { "tax_id": "TX-001" },
    "result": "approved"
  },
  "sanitized_payload": {
    "ssn": "[REDACTED_BY_POLICY]",
    "employee": { "tax_id": "[REDACTED_BY_POLICY]" },
    "result": "approved"
  }
}
```

> **Security note:** `original_payload` contains raw PII by design — it is the compliance record. `data/audit.jsonl` is gitignored and must be protected by filesystem ACLs in production.

## 11. Known Limitations / Future Work

- **Regex-based PII detection** (e.g. catching `123-45-6789` in an unrecognised field like `"ref_number"`) is not yet implemented. The current policy is key-name-based only.
- **List-of-dicts** payloads (e.g. `[{"ssn": "..."}]`) raise `GovernanceError` because `EnterpriseToolPayload` expects a dict root. A future PR could handle list roots by wrapping in `{"items": [...]}`.
- **Async audit writes** — currently blocking. For high-throughput deployments, consider an async queue + background writer thread.
