## 1. Executive Summary

v0.6.0 closes the read-only gap introduced in Phase 2: the Dead-Letter Queue could be
inspected via `GET /dlq` but had no recovery path. Phase 3 adds a single, operationally
critical endpoint — `POST /dlq/replay` — that lets an admin drain the entire DLQ and
re-admit every failed payload back into the primary RQ worker queue as a **fresh job**
with a fully reset retry counter.

| Directive | Implementation |
|---|---|
| Replay endpoint | `POST /dlq/replay` mounted on root app |
| Queue migration | Atomic `RPOP` drain → `queue.enqueue()` re-admission |
| Idempotency / fresh retry | New `Retry(max=3, interval=[2,4,8])` object; fresh UUID job ID |
| Response payload | `DlqReplayResponse` with `requeued`, `skipped`, `total_processed`, `message`, `skipped_details` |

## 3. Design Decisions

### 3.1 — `RPOP` (not `LPOP`)

The DLQ is built with `LPUSH` so the **head** (index 0) holds the most-recently-failed job.
Replay uses `RPOP` from the **tail**, which processes jobs in chronological order (oldest failure
first). This is the most natural reprocessing order: if job B depended on job A and both
failed, replaying A before B avoids B failing again on a missing dependency.

### 3.2 — Idempotency via Fresh Job UUID

The original `job_id` from the DLQ entry is **deliberately discarded**. RQ stores failed
job metadata in Redis under the original UUID. If we re-used the same ID:

1. The `queue.enqueue()` call would collide with the existing failed job record.
2. RQ behaviour on ID collision is undefined across versions.

A fresh UUID (generated by `job_id=None`) gives the replayed job a clean slate in every
RQ internal registry.

### 3.3 — Retry Counter Reset

Passing a new `Retry(max=settings.RQ_RETRY_MAX, interval=settings.RQ_RETRY_INTERVALS)`
object allocates a new `retries_left` counter at `RQ_RETRY_MAX` (default: 3). The worker
has no memory of the previous failure run — the job is treated as if submitted for the
first time via `POST /workflow/submit`.

### 3.4 — Enqueue Failure Recovery (no silent data loss)

```
RPOP  →  parse  →  enqueue()  ←── throws?
                                     │
                              RPUSH raw bytes back to DLQ tail
                              count as "skipped", add to skipped_details
```

If `queue.enqueue()` itself fails (e.g. transient Redis write timeout), the raw DLQ
bytes are immediately `RPUSH`-ed back to the tail of the list. The entry is counted as
`skipped` and its error is surfaced in `skipped_details`. No payload is silently lost.

### 3.5 — Poison-Pill Guard (malformed entries not restored)

Malformed entries (non-JSON bytes, valid JSON but missing/empty `payload` key) are
**permanently dropped** from the DLQ. If we restored them, they would be `RPOP`-ed on the
next replay call and fail identically — an infinite poison-pill loop. The original raw bytes
are logged at `WARNING` level for manual inspection from server logs.

### 3.6 — Async Safety (`run_in_executor`)

`replay_dlq()` is a **synchronous** function: it calls blocking Redis I/O (`rpop`,
`rpush`) and RQ's `queue.enqueue()` (also synchronous) in a tight loop. Calling it
directly inside an `async def` handler would block the entire uvicorn event loop for the
duration of the drain.

Solution: `await loop.run_in_executor(None, partial(replay_dlq, redis_conn, rq_queue))`
offloads the work to a thread-pool worker, keeping the FastAPI event loop fully
responsive for other in-flight requests.

## 5. Telemetry Lifecycle (v0.6.0 — Replay Path)

```
Admin triggers POST /dlq/replay
      │
      ▼
[REPLAY]  dlq.py:replay_dlq()
          INFO  [REPLAY] Job 'abc123' (workflow: 'pipeline-x')
                         re-enqueued as new job 'def456'.

          ... repeat for each DLQ entry ...

[REPLAY]  dlq.py:replay_dlq()
          INFO  [REPLAY] Complete — 5 requeued, 0 skipped,
                         5 total drained from 'asyncflow:dlq'.

[REPLAY]  main.py:replay_dlq_endpoint()
          INFO  [REPLAY] POST /dlq/replay — Replay complete:
                         5 job(s) successfully re-enqueued.

      ▼
Response:
{
  "requeued": 5,
  "skipped": 0,
  "total_processed": 5,
  "message": "Replay complete: 5 job(s) successfully re-enqueued.",
  "skipped_details": []
}

      ▼
Each replayed job re-enters the standard lifecycle:

[QUEUED]      → worker picks it up
[PROCESSING]  → process_workflow() executes steps
[RETRYING]    → (if step fails) RQ retries with backoff
[DLQ-SENT]    → (if all retries fail) route_to_dlq() fires again
```

## 8. Known Limitations

| Item | Notes |
|---|---|
| Replay is all-or-nothing | No filtering by `workflow_name` or `failed_at` range. A `?workflow=X` filter is a natural v0.7 addition. |
| DLQ list still grows unbounded | `POST /dlq/replay` drains the list on use, but between replays the key can grow large. Production should add periodic `LTRIM` or TTL-based eviction. |
| Replayed jobs get a new UUID | Clients polling the original `task_id` will not see replay progress. A `replayed_as` field written back to the DLQ entry could link old→new. |
| No partial replay | Cannot replay a single entry by `job_id`. Full drain-and-requeue is the only supported mode. |
| `attempt` counter in DLQ entry reflects original run | Since the entry is consumed (not mutated), this is only relevant if callers inspect DLQ history via external tooling. |
